*** General Commands
**** Files & folders
- Copy a single file

  #+begin_src powershell
  Copy-Item -Path "C:\Source\File.txt" -Destination "D:\Destination\"
  #+end_src

- Copy a folder and everything inside it

  #+begin_src powershell
  Copy-Item -Path "C:\Source\Logs" -Destination "D:\Backup\" -Recurse
  #+end_src

- Move a file (cut and paste)

  #+begin_src powershell
  Move-Item -Path "C:\Temp\report.pdf" -Destination "C:\Archive\"
  #+end_src

- Rename a file

  #+begin_src powershell
  Rename-Item -Path "C:\Temp\old.txt" -NewName "new.txt"
  #+end_src

- Delete a file

  #+begin_src powershell
  Remove-Item -Path "C:\Temp\junk.log"
  #+end_src

- Delete a folder and all its contents (careful)

  #+begin_src powershell
  Remove-Item -Path "C:\Temp\cache" -Recurse -Force
  #+end_src

- Create a new empty folder

  #+begin_src powershell
  New-Item -Path "C:\Projects\NewClient" -ItemType Directory
  #+end_src

- Create a new empty file

  #+begin_src powershell
  New-Item -Path "C:\Temp\notes.txt" -ItemType File
  #+end_src

- Check whether a file or folder exists (returns True/False)

  #+begin_src powershell
  Test-Path -Path "C:\Program Files\App\app.exe"
  #+end_src

** Building An MCP In Windows: Microsoft Learn - Claude Desktop :sequence:claude:mcp:
:PROPERTIES:
:NOTION:   https://app.notion.com/p/3a656b5770198056ae70dca475523aa4
:CREATED:  [2026-07-23 Thu]
:END:
Endpoint: =https://learn.microsoft.com/api/mcp=\\
Transport: Streamable HTTP (remote, Microsoft-hosted)\\
Auth: none required\\
Cost: free\\
Status: GA since 2025-11-07

Tools exposed:

- =microsoft_docs_search= — semantic search across official Microsoft technical documentation
- =microsoft_docs_fetch= — fetch a specific Learn URL, converted to markdown
- =microsoft_code_sample_search= — official Microsoft/Azure code snippets, optional language filter

Note: the endpoint returns =405 Method Not Allowed= in a browser. That is expected — it is not a web page.

--------------

**** Phase 1 — Connect Learn MCP to Claude Desktop (Windows)
- Add the Microsoft Learn MCP server to Claude Desktop on Windows
  - Confirm prerequisites
    - Claude Desktop for Windows is installed and you are signed in
    - Your Claude account is on a paid plan (Pro, Max, Team, or Enterprise) — custom connectors are gated to paid plans
    - Outbound HTTPS to =learn.microsoft.com= is not blocked by corporate firewall or TLS inspection
  - Open the connector settings
    - Launch Claude Desktop
    - Click your profile icon in the lower-left corner
    - Select Settings
    - Select Connectors in the left sidebar
    - Scroll to the bottom of the connector list
  - Add the custom connector
    - Click "Add custom connector" (labeled "Add Integration" under Integrations in some builds)
    - Set Name to: Microsoft Learn
    - Set Remote MCP server URL to: https://learn.microsoft.com/api/mcp
    - Leave OAuth Client ID and Client Secret blank — this server is unauthenticated
    - Click Add
  - Verify the connection
    - Confirm the connector shows a Connected or Enabled state, not an error
    - Click into the connector and confirm all three tools are listed and toggled on
      - microsoft_docs_search
      - microsoft_docs_fetch
      - microsoft_code_sample_search
    - Close Settings
  - Restart Claude Desktop cleanly
    - Right-click the Claude icon in the Windows system tray
    - Choose Quit — closing the window alone leaves the process running
    - Relaunch Claude Desktop from the Start menu
  - Smoke-test the connection
    - Start a new chat
    - Click the tools/attachment icon in the composer and confirm Microsoft Learn appears in the tool list
    - Ask a query that cannot be answered from training data, for example: "Use the Microsoft Learn tools to show me the current Intune enrollment restriction settings and where they live in the admin center menu today."
    - Confirm Claude visibly invokes a Microsoft Learn tool rather than answering from memory
  - Pin the behavior so the tools actually get used
    - Open Settings, then Profile (or "What personal preferences should Claude consider?")
    - Add a standing instruction along these lines:
      - "You have Microsoft Learn MCP tools available. For any question about Microsoft 365, Intune, Entra, Defender, or Azure — especially admin center navigation, current menu paths, licensing, or policy settings — call microsoft_docs_search or microsoft_docs_fetch before answering. Do not answer from training data alone, as Microsoft admin center UI changes frequently."
    - Save and restart Claude Desktop

--------------

**** Phase 1b — Fallback if the custom connector path is unavailable
Use this only if your Claude plan or a managed policy blocks custom connectors. It proxies the remote HTTP server through a local stdio bridge.

- Bridge the remote server locally with mcp-remote
  - Install Node.js LTS
    - Download the Windows x64 LTS MSI from nodejs.org, or run =winget install OpenJS.NodeJS.LTS= from an elevated PowerShell prompt
    - Open a new PowerShell window and confirm with =node --version= and =npx --version=
  - Locate the Claude Desktop config file
    - Press Win+R, paste =%APPDATA%\Claude=, press Enter
    - If =claude_desktop_config.json= does not exist, create it
    - Alternatively reach it via Settings, then Developer, then Edit Config
  - Edit the config
    - Open =claude_desktop_config.json= in a text editor

    - Insert the following, merging into an existing =mcpServers= block if one is present

      #+begin_src json
      {
        "mcpServers": {
          "microsoft-learn": {
            "command": "npx",
            "args": ["-y", "mcp-remote", "https://learn.microsoft.com/api/mcp"]
          }
        }
      }
      #+end_src

    - Save the file and validate that the JSON is well-formed — a trailing comma will cause a silent failure

  - Restart and verify
    - Quit Claude Desktop from the system tray, then relaunch
    - Confirm microsoft-learn appears in the tool list in a new chat
    - If it does not appear, check logs at =%APPDATA%\Claude\logs\mcp-server-microsoft-learn.log=

--------------

**** Phase 2 — Optional: live tenant data via Microsoft MCP Server for Enterprise
This is a separate server from Learn MCP. Learn MCP gives you documentation. This gives you read access to your actual Entra tenant — users, groups, applications, device insights, admin reporting. Public preview, read-only, no additional license beyond what you already hold for the data being accessed.

Do this only on a machine and tenant where you are authorized to register applications, and register it as a public client so no secret is stored on the workstation.

- Stand up Enterprise MCP for Claude Desktop
  - Confirm you hold sufficient Entra role to register an application and grant consent (Global Admin or Application Administrator plus Privileged Role Administrator)
  - Register the client application
    - Sign in to the Microsoft Entra admin center with your Global Admin account
    - Navigate to Identity, then Applications, then App registrations, then New registration
    - Name it something identifiable, for example: Claude Desktop MCP Client
    - Under Redirect URI, select the "Mobile and desktop applications" platform — this makes it a public client using authorization code flow with PKCE, which is the correct shape for a desktop app that cannot protect a secret
    - Record the Application (client) ID and Directory (tenant) ID
  - Grant the MCP permissions
    - Open API permissions for the new registration
    - Add the =MCP.<Microsoft_Graph_Scope>= permissions matching the read scopes you actually need — grant least privilege, not blanket Directory.Read.All
    - Click Grant admin consent for your tenant
  - Connect it in Claude Desktop
    - Consult the current setup instructions at github.com/microsoft/EnterpriseMCP for the live endpoint URL and OAuth parameters, as the preview endpoint has changed during rollout
    - In Claude Desktop, go to Settings, then Connectors, then Add custom connector
    - Enter the endpoint URL and the OAuth Client ID from your app registration
    - Complete the browser sign-in prompt with your Global Admin credentials
  - Set up auditing before you rely on it
    - All Enterprise MCP operations run under a fixed Microsoft app ID: =e8c77dc2-69b3-43f4-bc51-3213c9d915b4=

    - Filter Microsoft Graph activity logs on that AppId to review what was queried

    - Sample Kusto query for Log Analytics:

      #+begin_src text
      MicrosoftGraphActivityLogs
      | where TimeGenerated >= ago(30d)
      | where AppId == "e8c77dc2-69b3-43f4-bc51-3213c9d915b4"
      | project RequestId, TimeGenerated, UserId, RequestMethod, RequestUri, ResponseStatusCode
      #+end_src

**** Troubleshooting
| Symptom                               | Cause / fix                                                                                                                                                                            |
|---------------------------------------+----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Connector added but tools never fire  | Model is answering from training data. Add the system-prompt nudge in Phase 1, final step.                                                                                             |
| =405 Method Not Allowed=              | You opened the endpoint in a browser. Expected — the URL only works inside an MCP client.                                                                                            |
| Connection error on a work machine    | Corporate proxy or TLS inspection breaking the streamable HTTP session. Test =learn.microsoft.com= reachability, then check whether the proxy allows long-lived streaming connections. |
| "Add custom connector" button missing | Free plan, or an org-managed policy disabling custom connectors. Use the Phase 1b fallback.                                                                                            |
| Empty search results                  | Rephrase with narrower, more specific technical terms.                                                                                                                                 |
| Config edits have no effect           | Claude Desktop was closed but not quit. Exit from the system tray icon.                                                                                                                |
| Response payloads too large           | Append a token cap to the URL: =https://learn.microsoft.com/api/mcp?maxTokenBudget=2000=                                                                                               |

** Powershell: Disabling Spotlight Via CloudContent Policy         :sequence:
:PROPERTIES:
:NOTION:   https://app.notion.com/p/3c756b57701980a98cf6ccae76b62685
:CREATED:  [2026-08-25 Tue]
:END:
**** Minimum: current user
#+begin_src powershell
$p = 'HKCU:\SOFTWARE\Policies\Microsoft\Windows\CloudContent'
New-Item -Path $p -Force | Out-Null
New-ItemProperty -Path $p -Name 'DisableWindowsSpotlightFeatures' -Value 1 -PropertyType DWord -Force | Out-Null
#+end_src

This kills Spotlight on the lock screen along with Windows Tips and consumer feature content. Takes effect after sign-out/reboot.

If you want the lock screen only (leaving tips/desktop Spotlight alone), add these instead of — or alongside — the above:

#+begin_src powershell
$p = 'HKCU:\SOFTWARE\Policies\Microsoft\Windows\CloudContent'
New-Item -Path $p -Force | Out-Null
'DisableWindowsSpotlightOnSettings','DisableSpotlightCollectionOnDesktop' | ForEach-Object {
    New-ItemProperty -Path $p -Name $_ -Value 1 -PropertyType DWord -Force | Out-Null
}
#+end_src

**** Also flip the live state
The policy stops Microsoft from turning it back on, but the currently-applied background comes from ContentDeliveryManager. Clear it so the change is visible immediately:

#+begin_src powershell
$cdm = 'HKCU:\SOFTWARE\Microsoft\Windows\CurrentVersion\ContentDeliveryManager'
@{
    'RotatingLockScreenEnabled'        = 0
    'RotatingLockScreenOverlayEnabled' = 0
    'SubscribedContent-338387Enabled'  = 0   # lock screen spotlight
    'SubscribedContent-338388Enabled'  = 0   # suggested content
} .GetEnumerator() | ForEach-Object {
    Set-ItemProperty -Path $cdm -Name $_.Key -Value $_.Value -Type DWord -Force
}
#+end_src

**** Machine-wide / new profiles
Elevated, so it applies regardless of who logs in — write the policy into =HKLM= and into the default user hive so freshly created profiles inherit it:

#+begin_src powershell
# All-machine consumer content off
$hklm = 'HKLM:\SOFTWARE\Policies\Microsoft\Windows\CloudContent'
New-Item -Path $hklm -Force | Out-Null
'DisableWindowsConsumerFeatures','DisableCloudOptimizedContent','DisableConsumerAccountStateContent' |
    ForEach-Object { New-ItemProperty -Path $hklm -Name $_ -Value 1 -PropertyType DWord -Force | Out-Null }

# Seed the default profile
reg load HKU\DefUser C:\Users\Default\NTUSER.DAT | Out-Null
reg add "HKU\DefUser\SOFTWARE\Policies\Microsoft\Windows\CloudContent" /v DisableWindowsSpotlightFeatures /t REG_DWORD /d 1 /f | Out-Null
[gc]::Collect()
reg unload HKU\DefUser | Out-Null
#+end_src

To apply to every existing profile on a box, loop =HKU\<SID>= for each loaded hive plus each =NTUSER.DAT= under =C:\Users=.

**** Pin the image while you're at it
If you want a fixed lock screen picture that Spotlight can't displace (Enterprise/Education SKUs honor this):

#+begin_src powershell
$pz = 'HKLM:\SOFTWARE\Policies\Microsoft\Windows\Personalization'
New-Item -Path $pz -Force | Out-Null
Set-ItemProperty -Path $pz -Name 'LockScreenImage' -Value 'C:\ProgramData\Branding\lock.jpg' -Type String -Force
Set-ItemProperty -Path $pz -Name 'LockScreenOverlaysDisabled' -Value 1 -Type DWord -Force
#+end_src

For Intune, the equivalent CSP is =./User/Vendor/MSFT/Policy/Config/Experience/AllowWindowsSpotlightOnLockScreen= set to 0 — same registry target, just delivered as policy so it re-applies on every sync.

** Powershell: Pin Windows 11 Underline Access Keys Permanently    :sequence:

**** Fix: pin cues on permanently
GUI path is Settings → Accessibility → Keyboard → *Underline access keys*. From PowerShell:

#+begin_src powershell
$sig = @'
[DllImport("user32.dll", SetLastError=true)]
public static extern bool SystemParametersInfo(uint uiAction, uint uiParam, IntPtr pvParam, uint fWinIni);
'@
$spi = Add-Type -MemberDefinition $sig -Name Spi -Namespace Win32 -PassThru

# SPI_SETKEYBOARDCUES = 0x100B; SPIF_UPDATEINIFILE|SPIF_SENDCHANGE = 0x03
$spi::SystemParametersInfo(0x100B, 0, [IntPtr]1, 0x03)
#+end_src

Effective immediately, no sign-out, and it persists — the API writes through to =HKCU\Control Panel\Desktop\UserPreferencesMask= (byte 0, bit =0x20=) for you rather than making you get the polarity right by hand.

To verify it took:

#+begin_src powershell
$sigGet = @'
[DllImport("user32.dll", SetLastError=true)]
public static extern bool SystemParametersInfo(uint uiAction, uint uiParam, ref bool pvParam, uint fWinIni);
'@
$get = Add-Type -MemberDefinition $sigGet -Name SpiGet -Namespace Win32 -PassThru
$cues = $false
$get::SystemParametersInfo(0x100A, 0, [ref]$cues, 0) | Out-Null   # SPI_GETKEYBOARDCUES
$cues
#+end_src

Since you're doing this across machines anyway, the same =UserPreferencesMask= bit seeds into =C:\Users\Default\NTUSER.DAT= the same way as the Spotlight values, so new profiles come up with underlines already on.

**** Sli-Pad Dynamic Event URL Redirect + Show-Day iPad Setup
*Owner:* Mattie Aran (Lupine Tech Design)\\
*Project:* 418 Productions / Tallon — Interactive Event iPad Service\\
*Status:* Design / to build

#+begin_quote
/For URL Control without having to mess with the console mid-show/

#+end_quote

**** Architecture (plain language)
1. A tiny Vercel project serves a single permanent URL — e.g. =https://418-slido.vercel.app/=
2. That URL reads a stored value (the current event URL) and issues an HTTP redirect to it
3. The stored value lives in *Vercel Edge Config* — a key/value store that can be edited *without redeploying*
4. The Hexnode kiosk Web App points at the permanent URL, forever
5. Changing events = edit one value in the Vercel dashboard (or later, via an Apple Shortcut)

--------------

**** Critical technical constraints
These are not optional — getting them wrong causes field failures that are hard to diagnose.

- *Use a 302 or 307 redirect, never a 301.* A 301 is a /permanent/ redirect and browsers cache it aggressively. Ship a 301 once and devices may keep going to the old event even after the value changes — with no obvious way to clear it short of wiping browser data on every unit.
- *Send* *=Cache-Control: no-store=* on the redirect response so nothing intermediate caches it.
- *Devices only pick up a change on reload.* The redirect is evaluated when the page loads. Changing the target mid-session does nothing until each iPad reloads — via idle-refresh if enabled, a manual pull-to-refresh, or a kiosk toggle from the console. Plan the swap for /between/ sessions, not during one.
- *Store the full target URL*, including any query parameters the client's Slido link carries.
- *Test with the real Slido link before show day.* Confirm Slido's auth flow behaves normally when arrived at via redirect.

--------------

**** Build sequence
***** Phase A — Create the project (can be done entirely from an iPad)
No Mac required. Create the repo in GitHub's web interface, then import it to Vercel.

1. *Create a new GitHub repository* — name it something like =418-slido-redirect=. Private.
2. *Add file:* *=package.json=*

#+begin_src json
{
  "name": "418-slido-redirect",
  "private": true,
  "dependencies": {
    "@vercel/edge-config": "latest"
  }
}
#+end_src

1. *Add file:* *=api/redirect.js=*

#+begin_src javascript
import { get } from '@vercel/edge-config';

export const config = { runtime: 'edge' };

export default async function handler() {
  const target = await get('slidoTarget');

  if (!target) {
    return new Response('No event URL is currently set.', {
      status: 503,
      headers: { 'Cache-Control': 'no-store' }
    });
  }

  return new Response(null, {
    status: 302,
    headers: {
      Location: target,
      'Cache-Control': 'no-store'
    }
  });
}
#+end_src

1. *Add file:* *=vercel.json=* — routes every path to the redirect handler.

#+begin_src json
{
  "rewrites": [
    { "source": "/(.*)", "destination": "/api/redirect" }
  ]
}
#+end_src

***** Phase B — Deploy and wire up storage
1. *In Vercel: New Project > Import* the GitHub repo. Accept the defaults and deploy.
2. *Create an Edge Config store.* In the Vercel dashboard, go to Storage > Edge Config > Create. Name it =418-slido=.
3. *Connect the store to the project.* From the Edge Config's Projects tab, link =418-slido-redirect=. This automatically injects the connection string as an environment variable — no manual config needed.
4. *Add the item.* In the Edge Config's Items editor, add:
   - Key: =slidoTarget=
   - Value: a test Slido event URL (full =https://= URL)
5. *Redeploy once* after connecting the store, so the project picks up the new environment variable.
6. *Test in a browser:* load the Vercel URL. It should bounce straight to the Slido event.

***** Phase C — Point the kiosk at it
1. In the Hexnode UEM console: *Apps > Web Apps >* edit the Slido web app. Replace the event URL with the permanent Vercel URL. Keep the name generic.
2. Push/re-associate the kiosk policy to the test iPad.
3. *Validate the full loop:* confirm the iPad lands on the Slido event. Then change =slidoTarget= in Edge Config to a second test event, reload the iPad, and confirm it follows. That reload-follows-the-change behavior is the whole feature — verify it before trusting it.

--------------

**** Domain options
The kiosk URL is never seen by attendees, so a branded domain is polish, not a requirement.

| Option           | URL looks like               | Needs                                          | Notes                                    |
|------------------+------------------------------+------------------------------------------------+------------------------------------------|
| *Vercel default* | =418-slido.vercel.app=       | Nothing                                        | Works today. Recommended starting point. |
| *Lupine domain*  | =slido.lupinetechdesign.com= | Mattie's own DNS access                        | No Alex dependency.                      |
| *418 domain*     | =slido.418productions.com=   | A CNAME record from whoever controls 418's DNS | Cleanest for client-facing polish.       |

*Important reassurance for the 418 option:* adding a subdomain CNAME record does *not* affect email. Email routing is governed by MX records; a subdomain CNAME is a separate record that touches nothing Google Workspace or Microsoft 365 rely on. This is a low-risk ask.

*Practical note:* DNS for the 418 domain may be managed at the registrar rather than in Google Workspace — find out where the nameservers point before asking Alex for anything. Since the ABM (Apple Business Manager) verification also requires a domain TXT record with Alex present, *bundle both DNS asks into one conversation* rather than going back twice.

Start on the Vercel default URL. Migrating to a custom domain later is a Vercel dashboard setting plus one DNS record, and does not require rebuilding anything.

--------------

**** Later: the one-tap swap (v2)
Once the redirect is proven, the show-day motion can become a single tap instead of a dashboard visit.

*Build it as an Apple Shortcut, not a web app.* Shortcuts does authenticated HTTP requests natively, runs from the iPad Home Screen, needs no hosting, and takes minutes rather than a weekend. Design:

1. Shortcut prompts: "Paste event URL"
2. Sends an authenticated request that writes the new value
3. *Reads the value back and displays it for confirmation*

Step 3 is not optional. A write with no read-back, executed in front of a client, is how a show breaks quietly.

*Security constraints:*

- The write credential must never live in anything client-facing
- Hexnode's own API uses a /single global key for the entire portal/ — if a future version touches the Hexnode API directly rather than Vercel, that key is high-value and must be guarded accordingly
- Prefer writing to Vercel Edge Config over writing to Hexnode; the blast radius of a leaked credential is one redirect value versus the entire MDM portal

*Rehearsal rule:* swap URLs with the Shortcut cold, twice, on a non-show day before it is ever used in front of a client.

*** Our units
- *GJ2CQ Pucks*
  - the barrel-jack 2020 revision.

*Part 1 — What to actually call them*

There is no marketing name for the variants, but there *are* three distinct hardware revisions of the “Google Wifi” puck, and each has a real model number printed on the underside label. Use those.

| Revision   | Model #                  | FCC ID         | External tells                              |
|------------+--------------------------+----------------+---------------------------------------------|
| 1st (2016) | *NLS-1304-25*            | A4RNLS-1304-25 | USB-C power, engraved “G”, 2× GbE           |
| 2nd (2017) | *AC-1304*                | A4RAC-1304     | USB-C power, otherwise near-identical       |
| 3rd (2020) | *GJ2CQ* (SKU GA02430-US) | —            | *Barrel* power jack, “G” is a printed label |

The 2nd-gen AC-1304 dropped the Zigbee radio that was embedded in the original NLS-1304-25; the 3rd-gen revision's only notable outside change was migrating from USB-C to a barrel connector. All three are “Google Wifi” — what people call gen1 relative to Nest Wifi (gen2).

*On your button question:* the unit with the hidden/soft button is almost certainly the *GJ2CQ*. There's a well-known thread from someone who couldn't find the button at all on that model — the answer was that on the sticker with the QR code there's a circle right above the words “setup network,” and the button is underneath that circle; you press the circle and feel the button beneath it. The NLS-1304-25 and AC-1304 instead have a discrete button in the recessed port area on the back/side.

So: *“the GJ2CQ pucks”* or *“the barrel-jack 2020 revision.”* Flip one over and read the label to confirm.

*One correction to what you were told:* the two reset procedures aren't model-specific. Google documents both for all of these — hold-while-powered is primary, and unplug, hold the button, plug the power back in while holding for ~10 seconds is the documented /fallback/ when the first doesn't take. You can use either on your GJ2CQs.

*** Part 2 — Troubleshooting
*Sequence A: get a clean reset first*

Your solid-blue-that-never-pulses is the thing to fix before touching the app.

1. Unplug the two problem pucks. Leave them off 60 seconds.
2. Hold the membrane button, plug power in while holding, keep holding ~15 s past power-on. Release when it flashes blue.
3. *Now walk away for 15 minutes.* This is the big one. The pucks take about 5 minutes to actually be ready after a factory reset, but they show a blue light after about a minute — which is a lie, and falling for it just slows you down. Google's own docs also say the reset itself can take up to 10 minutes.
4. Watch the pattern at the 15-minute mark:
   - *Pulsing/breathing blue* → ready, go to Sequence B.
   - *Solid blue cycling on ~23 s, off 1–2 s, repeating* → that's a boot loop, not a reset. See the note at the bottom.

*Sequence B: the QR-scan / direct-Wi-Fi handoff*

Run this with *only one un-provisioned puck powered on at a time.* The setup program auto-connects to the first unconfigured puck it detects and rarely lets you choose between two, so when you scan the QR code it complains it's the wrong one. If both of your problem pucks have been plugged in simultaneously, that alone could explain the failures.

1. Physically move the puck to within a few feet of the primary. During setup the two pucks must link over Wi-Fi, which refuses to work unless the signal is very strong — you can relocate it afterward and it'll report good-to-excellent.
2. Unplug the /working satellite/ temporarily. It reduces contention and removes one more thing for the app to latch onto.
3. On the iPhone, before scanning:
   - Bluetooth *on* (initial handshake is BLE, not Wi-Fi)
   - Settings → Google Home → *Local Network* enabled
   - Turn *Airplane-mode-off but cellular data off*, so the phone can't bail to LTE mid-handoff
   - Join your primary's SSID, then Settings → Wi-Fi → (i) → *Private Wi-Fi Address off*
4. Force-quit and reopen Google Home. Scan.
5. If the scan resolves but the Wi-Fi join stalls: iOS sometimes silently declines the setup SSID. Manually check Settings → Wi-Fi for a network beginning with setup or the puck's name and join it by hand, then return to Home.
6. If the QR won't take at all, use the *manual setup key* on the label instead of the camera.

*Sequence C: fallbacks*

- *Wired*: plug the point into a LAN port on the primary before adding it. Sometimes gets past a flaky wireless handshake.
- *Different phone*, ideally Android. The iOS Home app setup path for these older pucks is meaningfully flakier and this is worth 10 minutes before you write a unit off.
- *New Wi-Fi network test*: set the problem puck up as a /primary/ on a throwaway network. If it can create a network, the radio and flash are fine and the issue is the add-a-point flow. If it can't, it's the unit.

*The unhappy possibility*

If a puck boot-loops on solid blue after a proper reset and 15-minute wait, that's usually eMMC failure — the 4 GB flash module in these has a known wear-out failure mode, and it's the most common way old Google Wifi and OnHub units die. There's no field fix. Given you got four used units and two came up clean, two dead-flash pucks is entirely plausible. Run Sequence B once properly before concluding that, though — the one-at-a-time rule and the 15-minute wait resolve a surprising number of these.

**** 2. HOW THE SYSTEM WORKS
Each laptop's disk is partitioned as:

| Partition | Size      | Purpose                                 |
|-----------+-----------+-----------------------------------------|
| EFI (ESP) | 260 MB    | Boot files (FAT32)                      |
| MSR       | 16 MB     | Reserved                                |
| OS        | remainder | Windows, label =OS=                     |
| RESET     | ~45 GB    | Hidden payload partition, label =RESET= |

The *RESET partition* holds three things:

- =baseline.wim= — the golden master image (~29.7 GB on Dell)
- =winpe.wim= — the auto-run WinPE that performs the reset (~356 MB)
- =Boot\boot.sdi= — the ramdisk descriptor

A *BCD boot entry* ("Reset to Baseline") ramboots =winpe.wim= from the RESET partition. That WinPE's =startnet.cmd= calls =reset.cmd=, which formats the OS volume, re-applies =baseline.wim=, rewrites boot files with =bcdboot=, logs, and reboots into a pristine machine.

*To trigger a reset* (elevated *cmd*, not PowerShell):

#+begin_src text
bcdedit /bootsequence {reset-guid}
shutdown /r /t 0
#+end_src

=/bootsequence= is a one-shot next-boot-only override — it does not change normal boot behavior.

**** 3. VOCABULARY
*Two computers:*

- *WORKBENCH* — separate x64 Windows PC with the Windows ADK installed. Builds WinPE media, stores master images. Never wiped.
- *TARGET* — the laptop being imaged.

*USB sticks (always referred to by these names, physically labeled and color-coded):*

| Name                  | Color        | Role                                                                                                                                                                            | Bootable? |
|-----------------------+--------------+---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------+-----------|
| *WIN-INSTALLER-STICK* | Green        | Windows 11 install media (Media Creation Tool)                                                                                                                                  | Yes       |
| *X-BOOT-STICK*        | Red          | Interactive WinPE — boots to bare =X:\>=, does nothing on its own. Capture + rescue + provisioning. *SAFE.*                                                                   | Yes       |
| *AUTO-RESET-STICK*    | Purple       | Auto-run WinPE — boots straight into wipe+reimage. *LIVE AMMUNITION.* Mostly exists as the =winpe.wim= file on each RESET partition; the stick is a rare manual-rescue spare. | Yes       |
| *FERRY-STICK*         | Blue         | Generic exFAT transport — drivers, installers, docs, payload files                                                                                                            | No        |
| *IMAGE-STICK*         | Black 256 GB | Holds the golden =baseline-dell.wim= / =baseline-lenovo.wim=                                                                                                                    | No        |

The three bootable sticks are *hardware-agnostic* — the same Red/Purple/Green work on Dell and Lenovo. Only the image files are variant-specific.

*The two WinPE sticks look identical in a file listing.* The only difference is inside =boot.wim= at =\Windows\System32\startnet.cmd=:

- =wpeinit= only → *X-BOOT-STICK* (interactive/safe)
- =wpeinit= + =call X:\Windows\System32\reset.cmd= → *AUTO-RESET-STICK* (wipes)

To verify which is which:

#+begin_src text

type C:\peek\Windows\System32\startnet.cmd
cd C:\
dism /Unmount-Image /MountDir:C:\peek /Discard
rmdir C:\peek
dism /Get-MountedImageInfo
#+end_src

**** 4. CURRENT IMAGING PROCESS (fleet rollout — the fast path)
*Key principle:* fleet machines get *no Windows install and no OOBE*. A clean install would just be scaffolding that the image apply overwrites. Everything is provisioned directly from WinPE.

Per machine, hands-on time is roughly *15 minutes*; the DISM apply (15–25 min) is unattended, so 3–4 machines run staggered in parallel.

***** Step 0 — BIOS prep (per machine)
Dells often ship with storage in *RAID/Intel RST/VMD* mode, which makes the internal SSD *invisible to WinPE and diskpart*. In BIOS (F2):

- *Storage → SATA/NVMe Operation → AHCI*
- *Boot order → put USB above Windows Boot Manager* (avoids the F12 race)
- *Fast Boot → Thorough* if available

#+begin_quote
After switching to AHCI, the existing Windows install will fail to boot and drop into recovery. This is expected and harmless — the disk is about to be wiped. Setting USB first in the boot order sidesteps it entirely.

#+end_quote

***** Step 1 — Boot the X-BOOT-STICK, build the partition layout
At =X:\>=:

#+begin_src text
diskpart
  list disk                     (CONFIRM disk 0 = internal SSD by size, NOT the USB)
  select disk 0
  clean
  convert gpt
  create partition efi size=260
  format quick fs=fat32 label="SYSTEM"
  assign letter=S
  create partition msr size=16
  create partition primary
  shrink desired=45000
  format quick fs=ntfs label="OS"
  assign letter=W
  create partition primary
  format quick fs=ntfs label="RESET"
  assign letter=R
  exit
#+end_src

***** Step 2 — Stage the RESET partition from the FERRY-STICK
Confirm letters first (=diskpart= → =list volume=), then:

#+begin_src text
robocopy D:\ R:\ /E /COPY:DAT /R:2 /W:2
#+end_src

or individually:

#+begin_src text
copy E:\baseline-<variant>.wim R:\baseline.wim
copy E:\winpe.wim R:\winpe.wim
mkdir R:\Boot
copy E:\boot.sdi R:\Boot\boot.sdi
#+end_src

***** Step 3 — Apply the golden image (this is where Windows is created)
#+begin_src text
Dism /Apply-Image /ImageFile:R:\baseline.wim /Index:1 /ApplyDir:W:\ /CheckIntegrity
#+end_src

***** Step 4 — Write boot files
#+begin_src text
bcdboot W:\Windows /s S: /f UEFI
#+end_src

***** Step 5 — Reboot into the new Windows
#+begin_src text
wpeutil reboot
#+end_src

Remove the USB. The machine boots to the auto-logged-in =AVTech= desktop — it is now a clone.

***** Step 6 — Create the reset BCD entry (from inside Windows — the proven method)
Run =make-reset-entry.bat= as administrator. *Before running, confirm the RESET partition is mounted as* *=R:=* *in Windows* — the script hard-codes =partition=R:= and binds to whatever =R:= resolves to at run time.

#+begin_src shell
@echo off
setlocal enabledelayedexpansion
for /f "tokens=2 delims={}" %%A in ('bcdedit /create {ramdiskoptions} /d "Reset ramdisk"') do set RDO={%%A}
bcdedit /set {ramdiskoptions} ramdisksdidevice partition=R:
bcdedit /set {ramdiskoptions} ramdisksdipath \Boot\boot.sdi
for /f "tokens=2 delims={}" %%A in ('bcdedit /create /d "Reset to Baseline" /application osloader') do set GUID={%%A}
bcdedit /set !GUID! device ramdisk=[R:]\winpe.wim,{ramdiskoptions}
bcdedit /set !GUID! osdevice ramdisk=[R:]\winpe.wim,{ramdiskoptions}
bcdedit /set !GUID! path \windows\system32\boot\winload.efi
bcdedit /set !GUID! systemroot \windows
bcdedit /set !GUID! detecthal yes
bcdedit /set !GUID! winpe yes
echo !GUID! > R:\reset-entry-guid.txt
echo === Created reset entry: !GUID! ===
pause
#+end_src

Verify before trusting it:

#+begin_src text
bcdedit /enum osloader
bcdedit /enum {ramdiskoptions}
type R:\reset-entry-guid.txt
#+end_src

***** Step 7 — Acceptance test
Fire one reset on the unit. A machine that resets clean and lands pristine is correct by definition. Then sticker it (serial + assigned M365 username) and log it on the tracking sheet.

**** 7. KNOWN LANDMINES (all previously hit and solved)
1. *Autopilot re-hijack.* Wiping a disk does not clear the cloud hardware hash. A machine that reaches the internet at OOBE while still registered gets re-enrolled. Deregister the serial from Autopilot /and/ install offline. (Less relevant on the fast path, since fleet machines never run OOBE — but stale enrollments should still be cleared in bulk.)
2. *=diskpart=* *cannot select a volume by label.* =select volume OS= is invalid syntax — only a number or a drive letter works. This caused repeated silent reset failures ("no volume selected" → format fails → apply fails).
3. *WinPE assigns different drive letters than full Windows.* Verify with =list volume= on each new hardware type before trusting an automated reset. Both variants here came up OS=C, RESET=D, ESP=volume 2 in WinPE.
4. *FAT32 32 GB ceiling.* =MakeWinPEMedia= cannot format a >32 GB stick as FAT32. Keep bootable sticks ≤32 GB. Does not apply to file-copy sticks (FERRY-STICK can be exFAT, any size). Also: =baseline.wim= is ~30 GB, which *exceeds FAT32's 4 GB single-file limit* — ferry sticks must be exFAT or NTFS.
5. *DISM partial unmount.* Always run =dism /Unmount-Image= from =C:\=, never from inside the mount tree. If a mount wedges: =dism /Cleanup-Mountpoints=.
6. *BitLocker auto-enables* on recent Windows 11. Before capture: =manage-bde -off C:= and set =HKLM\SOFTWARE\Policies\Microsoft\FVE\PreventDeviceEncryption=1=.
7. *Image must fit the RESET partition.* A 96%-full capture failure occurred on the Dell. Trim installers, extra .NET runtimes, vendor apps, and the ODT download cache before capturing.
8. *BCD scripting quirks.* =for /f= and ={braces}= break in PowerShell — run BCD work from *cmd* or a =.bat=. In a =.bat=, loop variables must be doubled (=%%A=) and variables read with delayed expansion (=!GUID!=), because plain =%GUID%= is evaluated at parse time and comes back empty.
9. *Identity residue in the image.* Signing out of Office is not enough — Edge can still /suggest/ a previously-used account because it reads from the Windows account broker. Full scrub requires clearing the Edge profile, the WAM/TokenBroker account store, and Credential Manager, then confirming =dsregcmd /status= shows =AzureAdJoined : NO=.

**** 8. OPEN ISSUES (current, limited)
***** 8.1 — Two Dells fail at the reset boot /(active, highest priority)/
*Symptom:* the machines image successfully and boot into Windows fine. On restart, selecting the reset entry goes straight to an error screen about something "not being connected" and Windows being unable to load — it never reaches the WinPE =X:\>= environment. 11 previous machines worked with the identical process.

*Since the method is proven, this is machine-specific. The reset entry points at three things; one is wrong on these units:*

- =boot.sdi= — via =ramdisksdidevice partition=R:= + =ramdisksdipath \Boot\boot.sdi=
- =winpe.wim= — via =ramdisk=[R:]\winpe.wim=
- The RESET partition binding itself

*Leading hypothesis:* =make-reset-entry.bat= hard-codes =partition=R:=, and bcdedit resolves that drive letter into a partition identifier *at the moment the script runs*. If the RESET partition was not mounted as =R:= in Windows at that time (different letter, or not mounted), the entry binds to the wrong partition — or to nothing — while still reporting "The operation completed successfully" for every line.

*Secondary hypotheses:* =winpe.wim= or =Boot\boot.sdi= missing, zero-length, or a partial/failed copy on those two units.

*Diagnostic sequence (on a failing unit, in Windows, elevated):*

#+begin_src text
diskpart
  list volume        (what letter does RESET actually have?)
  exit

dir R:\winpe.wim          (should be ~356 MB)
dir R:\Boot\boot.sdi      (should exist)
dir R:\baseline.wim       (should be ~29.7 GB)

bcdedit /enum osloader
bcdedit /enum {ramdiskoptions}
#+end_src

Confirm =ramdisksdidevice= points at the correct partition and =ramdisksdipath= is =\Boot\boot.sdi=.

*Fix:* ensure RESET is mounted as =R:= and both files are present and full-size → delete the bad entry (=bcdedit /delete {guid} /f=) and the misconfigured ={ramdiskoptions}= object → re-run =make-reset-entry.bat= → verify with =bcdedit /enum osloader= *before* rebooting.

***** 8.2 — Orphaned duplicate reset entries
Every run of =make-reset-entry.bat= creates a *brand-new* osloader entry. Re-running it (as happened during troubleshooting) leaves stale "Reset to Baseline" entries in the BCD store. Functionally harmless but confusing. Audit with =bcdedit /enum osloader=; delete stale ones with =bcdedit /delete {old-guid} /f=, keeping the GUID recorded in =R:\reset-entry-guid.txt=.

***** 8.3 — Reset entry not visible on the boot menu
=bcdedit /enum= only lists entries present in =displayorder=. An entry can exist and work while being invisible there. =/bootsequence= (the one-shot trigger) does *not* add anything to the menu. To expose it deliberately:

#+begin_src text
bcdedit /displayorder {current} /addfirst
bcdedit /displayorder {reset-guid} /addlast
bcdedit /default {current}
bcdedit /timeout 5
#+end_src

Always verify =default= points at Windows, not the reset entry.

***** 8.4 — GUIDs look identical at a glance /(resolved — not a bug)/
BCD uses time-based (v1) GUIDs, so every GUID minted on a given machine shares the same trailing block (encoding node + clock sequence). Only the *first segment* differs. Entries that appear identical in a photo or quick scan are usually distinct. Compare the first block carefully before concluding anything is corrupted.

***** 8.5 — Dell AHCI switch drops into recovery /(understood, has workaround)/
Switching storage mode from RAID to AHCI leaves the pre-existing Windows install unbootable, so the machine lands in recovery before the USB can be selected. Harmless — the disk is about to be wiped. Workaround: while already in BIOS, set *USB above Windows Boot Manager* in the boot order and *Fast Boot → Thorough*. Alternatively reach the USB via recovery → Troubleshoot → /Use a device/, or → /UEFI Firmware Settings/.

***** 8.6 — Apps fail to launch on first try after a fresh image /(minor, likely benign)/
On a freshly applied image, some apps (Notepad, PowerShell observed) do nothing on the first click and work on the second. Most likely normal first-run initialization after a DISM apply (permission repair, execution-alias registration, Defender caching a not-yet-seen binary). Worth a line on the tech card: /"if an app doesn't open on the first click, click again — normal right after a reset."/ Would only warrant investigation if it produces an actual error, or recurs after *every* reset rather than only the first.
